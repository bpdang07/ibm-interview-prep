    “Write a simple app, then containerize it”
    Flask API → Docker image → container
    
          
    A reported Cloud Software Developer question. Keep the app tiny so the conversation is about the container: why each line of the Dockerfile is there, and how the image gets to the cloud.
    
          
    
            
    
              
    app.py
    

    import os
from flask import Flask, jsonify

app = Flask(__name__)

# Kubernetes and load balancers call this to check the app is up
@app.get("/health")
def health():
    return jsonify(status="ok")

@app.get("/hello/<name>")
def hello(name):
    # Config comes from environment variables, not the code
    version = os.environ.get("APP_VERSION", "dev")
    return jsonify(message=f"Hello, {name}!", version=version)

    Dockerfile
    

    FROM python:3.12-slim
WORKDIR /app

# Dependencies first: editing app.py won't re-run pip install
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .

# Don't run as root inside the container
RUN useradd --create-home appuser
USER appuser

EXPOSE 8080
# 0.0.0.0, not 127.0.0.1, so traffic from outside the container gets in
CMD ["gunicorn", "--bind", "0.0.0.0:8080", "app:app"]

    What they'll likely ask next
    
            
    Why copy requirements.txt before the rest of the code?
    Each instruction is a cached layer. Dependencies change rarely and code changes constantly, so installing first means a code edit only rebuilds the last layers, and builds take seconds instead of minutes.
    
            
    What's the difference between an image and a container?
    The image is the read-only template you built. A container is one running instance of it, with its own small writable layer. You can run many containers from one image.
    
            
    Why gunicorn instead of flask run?
    Flask's built-in server is for development only: one process, no tuning. gunicorn is a production server that runs several worker processes and restarts any that crash.
    
            
    How would you make the image smaller?
    A slim base image, a .dockerignore so junk isn't copied in, --no-cache-dir on pip, and a multi-stage build when something has to be compiled: build in one stage and copy only the result into a clean final stage.
    
            
    Where would a database password go?
    Never in the image or the Dockerfile, since anyone with the image can read them. Inject it at runtime as an environment variable or mounted file from a secrets manager or a Kubernetes Secret.
    
            
    How would Kubernetes use the /health route?
    As a readiness probe (don't send traffic until it answers) and a liveness probe (restart the container if it stops answering). That's how a rolling update knows a new version is healthy before moving on.

    Lambda in practice
    POST /items → Lambda → DynamoDB
    
          
    How the pieces connect: an API Gateway route invokes the function, the function's IAM role lets it write to one table, its environment variable says which table, and everything it prints lands in CloudWatch Logs. Diagrams of bigger AWS designs are on the Design tab.
    
          
    
            
    
              
    src/app.py: the function
    

    import json
import os
import boto3

# Runs once per container and is reused while it stays warm
table = boto3.resource("dynamodb").Table(os.environ["TABLE_NAME"])

def handler(event, context):
    # API Gateway passes the request body as a string
    body = json.loads(event.get("body") or "{}")
    item = {"id": context.aws_request_id, "name": body.get("name", "")}
    table.put_item(Item=item)
    print("created", item["id"])   # → CloudWatch Logs
    return {
        "statusCode": 201,
        "headers": {"Content-Type": "application/json"},
        "body": json.dumps(item),
    }

    Sliding window
    Python
    

    # Longest substring without repeating characters
def longest(s):
    seen = {}            # char -> last index
    left = best = 0
    for right, ch in enumerate(s):
        if ch in seen and seen[ch] >= left:
            left = seen[ch] + 1   # jump past the repeat
        seen[ch] = right
        best = max(best, right - left + 1)
    return best          # O(n) time
    
          
    
          
    
            
    BFS on a grid
    Python
    

    from collections import deque

def num_islands(grid):
    rows, cols, count = len(grid), len(grid[0]), 0
    for r in range(rows):
        for c in range(cols):
            if grid[r][c] != "1": continue
            count += 1
            q = deque([(r, c)]); grid[r][c] = "0"
            while q:
                y, x = q.popleft()
                for dy, dx in ((1,0), (-1,0), (0,1), (0,-1)):
                    ny, nx = y + dy, x + dx
                    if 0 <= ny < rows and 0 <= nx < cols and grid[ny][nx] == "1":
                        grid[ny][nx] = "0"; q.append((ny, nx))
    return count          # O(rows * cols)
    
          
    
          
    
            
    Binary search
    Python
    

    def search(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo <= hi:
        mid = (lo + hi) // 2
        if nums[mid] == target: return mid
        if nums[mid] < target: lo = mid + 1
        else: hi = mid - 1
    return -1             # O(log n)
    
          
    
          
    
            
    SQL you should write cold
    SQL
    

    -- Nurses with 3+ scheduled assignments, busiest first
SELECT n.name, COUNT(a.id) AS assignments
FROM nurse n
JOIN assignment a ON a.nurse_id = n.id
WHERE a.status = 'scheduled'
GROUP BY n.name
HAVING COUNT(a.id) >= 3
ORDER BY assignments DESC;
-- Also know: LEFT JOIN vs INNER JOIN, WHERE vs HAVING,
-- ROW_NUMBER() OVER (PARTITION BY ... ORDER BY ...)
